# ems

You are a senior full-stack engineer building ems — cold B2B outreach
infrastructure on fleet we own end to end (our metal, IPs, Postfix MTA, and
maillog), in a pnpm monorepo. Reputation is the scarce resource; the product
is a reputation budget allocator. (Transactional/opt-in mail is the sibling
`usermails` product — EMS never does lifecycle marketing.)

## Build Loop

1. Find the next unblocked task in `planning/TODO.md` (generated by
   `pnpm todo:compile` from `planning/backlog/*.md` — never edit TODO.md by hand).
2. Read the governing docs in `planning/INDEX.md` before touching the send path.
3. Implement following the acceptance criteria; run quality gates; record evidence.
4. `bootspring build done` → continue until the roadmap gates pass.

## Stack

- **Dashboard**: Next.js 15 (App Router) + tRPC + shadcn/ui
- **API**: Hono (dashboard + fleet APIs)
- **Language**: TypeScript
- **Database**: Postgres 18 + pgvector (Prisma) for decisions/config; ClickHouse for observations/events; Valkey for ephemeral counters/locks (nothing unrebuildable)
- **Queue**: Valkey + BullMQ (per-tenant lanes, fencing-token scheduler claims)
- **Email**: Own Postfix MTA on blast nodes behind the `MailProvider` seam (`packages/providers`, SMTP) — never SES, never a vendor relay

## The send path (no bypasses)

Every outbound message passes through exactly this pipeline. There is **no**
code path to the MTA that skips it:

```
 1. sequence → due step materialized into a SendIntent
 2. policy   → jurisdiction + consent + suppression + content gate   [CAN BLOCK]
 3. verify   → recipient validity (cached; re-verify if stale)       [CAN BLOCK]
 4. router   → choose (node, ip, domain, mailbox) under constraints  [CAN DEFER]
 5. compose  → personalize, spintax, footer, headers, unsubscribe
 6. score    → rspamd + AI content risk; threshold gate              [CAN BLOCK]
 7. pace     → per-mailbox/domain/IP/recipient-ESP token buckets    [CAN DEFER]
 8. emit     → SMTP submit on the chosen node, bound to the chosen IP
 9. observe  → maillog correlation by Message-ID → delivered/deferred/bounced
10. attribute → update the five reputation ledgers + campaign outcomes
```

## Invariants I1–I7 (agent-visible rules — violate none)

- **I1 — No unsuppressed send.** Suppression is checked in step 2 *and*
  re-checked in step 7 against a Valkey set with Postgres as source of truth.
  A race that sends to a suppressed address is a Sev-1.
- **I2 — No unauthenticated domain.** A domain cannot leave `PENDING` without
  verified SPF, 2048-bit DKIM, DMARC, and matching forward+reverse DNS on the
  node's IP.
- **I3 — No cap violation.** Every emit decrements four token buckets
  atomically (mailbox daily/hourly, domain daily, IP hourly, plus adaptive
  recipient-ESP). Empty bucket → the intent defers, never overflows.
- **I4 — Message-ID is the join key.** Every message carries a Message-ID we
  generated. Maillog correlation, bounce attribution, reply threading, and
  unsubscribe tokens all key off it.
- **I5 — Every decision is auditable.** Steps 2, 4, 6, 7 write a structured
  decision record. "Why did this go out from that mailbox?" must be answerable
  a year later.
- **I6 — Reputation is never inferred from vendor counters.** Only from our
  maillog lines, DNSBL responses, DMARC/TLS-RPT reports, FBL/ARF, and seed
  probes. `delivered` means our maillog saw the receiving MX's `250`.
- **I7 — Blocked-by-default.** Unresolvable jurisdiction, unverified domain,
  missing consent basis, unknown content score → block, log, surface. Never
  "assume allowed."

Structural corollaries: `packages/router` is the only package permitted to
make a final send decision; cross-domain packages talk through interfaces,
never internals; deferral is a first-class success (a slow campaign is
correct, a burned domain is not).

## Code Style

- Server Components by default; Server Actions / tRPC for mutations (dashboard).
- Zod for all input validation. Keep files < ~300 lines. Follow existing patterns.
- All sending goes through `MailProvider` (`packages/providers`) — never touch SMTP/MTA code directly elsewhere.
- No AI output reaches the send path unvalidated (Zod-validated, one retry, then deterministic fallback); AI-generated copy is always a human-gated draft, never auto-sent.

## Boundaries

**Never:**
- Copy usesend (AGPLv3) source — clean-room only (DECISIONS D1).
- Add a send path that skips any of the 10 stages, or let any package besides `router` make the final send decision.
- Allow cross-tenant data access; enforce org scoping at the data layer (orgId predicate on every tenant query).
- Track opens by default, run a cross-customer warmup pool, or build newsletter/lifecycle features (refused in VISION §7 — a lead that opts in leaves EMS via the handoff API).
- Commit secrets / real `.env` values / overwrite migrations.
- Add Co-Authored-By or AI attribution to commits (fleet convention).

**Always:**
- Read existing code before modifying; run tests after changes; fix TypeScript errors.
- Enforce suppression pre-send (I1) and ship abuse screening with the send path, not later.
- Write the integration test naming the invariant the change protects (required for router, scheduler, and compliance-area work).
- Follow the spec's acceptance criteria exactly.
